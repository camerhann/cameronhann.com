Flood risk is sold as a map. It isn't. It is a claim about how water moves, a piece of software that has to run, and a team that will still be there when a planner, an underwriter, or a board asks: are you sure?

I spend my time on all three. Most people pick one.

**Models.** A flood model is a claim. If the claim is wrong, everything downstream is theatre — the FRA, the premium, the early warning. I care about the claim. QMED that matches WINFAP. Terrain that is actually two metres. A frequency analysis that admits its dispersion floor. The work is not "AI for flood." The work is making the physics and the statistics honest enough that a professional can rely on them.

**Software.** Honest models that live in a desktop app from 2003 do not compound. WINFAP crashes. ReFH2 has no undo. The method is copied into Excel and then into Word. That is not a workflow. That is a loss of institutional memory every time someone leaves.

[Hydrometric](https://hydrometric.io) exists because the statistical pathway should take seconds, show its working, and be auditable. [7Analytics](https://7analytics.ai) exists because insurers cannot price pluvial risk from a 1-in-100 outline drawn for planning. [Aegaea](https://aegaea.com) exists because a developer still needs a signed report that will survive a case officer.

The software is how the model becomes a system.

**Teams.** None of this holds if one person *is* the model. I have built Aegaea so it can issue without me in the loop. Same problem in software: if the method lives in my head, it is not a method. System design is the work of making other people faster than I am.

I do not think of these as three jobs. A model no one can run is a paper. Software with no model is a wrapper. A team with neither is a billing machine. The interesting work is the joint.

That is what I write about here. Long form, because the short version is already on X, and X is where nuance goes to die. If an essay is any good I will put a sharp version there and point back.
